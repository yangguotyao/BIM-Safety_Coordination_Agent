# 中英文双语展示设计方案

> 目标：在现有平台增加中英文切换，英文仅作为展示层投影，不改变任何业务语义、数据与智能体行为。
> 版本：v1（设计稿，未实施）

---

## 1. 设计原则

**中文是系统唯一的业务语义与数据基准，英文只是展示层投影。**

由此推导出四条硬约束：

| 约束 | 含义 |
|---|---|
| 数据不动 | SQLite 中的案例、证据、规则、记忆、事件全部保持中文，不新增语言字段 |
| 逻辑不动 | Agent 提示词、工具路由、风险规则、状态机、验收用例一律不改 |
| 翻译在读出侧 | 翻译只发生在「接口响应组装」与「文档导出」两条路径，不进入写入路径 |
| 可回退 | 任一时刻切回中文，展示立即恢复原文，无残留状态 |

---

## 2. 为什么不用「提示词限定英文输出」

不建议让各业务 Agent 自己决定输出语言，原因如下：

1. **大量文本并非 LLM 生成**：状态标签、风险等级、检查项名称、协同冲突描述、验收结论等由 Python 模板拼接，改提示词覆盖不到。
2. **改动面失控**：`agent.py`、`live_model.py`、`assurance.py`、`coordinator.py` 各自持有一段提示词，逐一修改容易遗漏，且难以回归。
3. **污染记忆与检索**：英文回答会写入对话记忆与 `agent_events`，影响后续中文检索、上下文继承和历史回放。
4. **切回中文不可逆**：已生成的英文记录无法还原成原始中文表述。
5. **安全信息易误译**：规则编号、条款号、阈值、GUID、单位在模型自由生成时可能被改写。

结论：**语言不进入业务链路，只在展示链路生效。**

## 3. 总体架构

```
┌──────────────────────── 前端（Vue 3） ────────────────────────┐
│  store.locale: 'zh' | 'en'  ← localStorage 持久化              │
│                                                                │
│  ① 静态文案层：导航 / 标题 / 按钮 / 表单 / 状态标签 → i18n 词条 │
│  ② 动态文本层：接口返回的中文字段 → 后端已译好的英文字段        │
└────────────────────────────────────────────────────────────────┘
                              │ 每个请求携带 X-Display-Lang: en
                              ▼
┌──────────────────────── 后端（FastAPI） ───────────────────────┐
│  ③ 翻译投影层 app/translation.py                                │
│     translate_fields(dict, lang) → 只替换展示字段，保留原结构    │
│     缓存：translation_cache 表（原文哈希 → 译文）                │
│  ④ 导出层 word_report.report(bundle, lang)                      │
└────────────────────────────────────────────────────────────────┘
                              │
                              ▼
                     业务层完全不变（agent / services / tools / rules）
```

三层职责互不越界：静态文案由前端词条解决，动态文本由后端翻译服务解决，导出由 Word 生成器按语言分支解决。

## 4. 语言状态与传递

### 4.1 前端状态

在 `src/store.ts` 的 `store` 中增加：

```ts
locale: (localStorage.getItem('bim-locale') as 'zh' | 'en') || 'zh'
```

切换函数 `setLocale(next)`：写入 store + localStorage + `document.documentElement.lang`，并触发当前页面数据重新拉取。

### 4.2 请求头

在 `src/api.ts` 的 `request()` 与 `download()` 中统一附加：

```ts
headers.set('X-Display-Lang', store.locale)
```

后端用依赖项读取，默认 `zh`，仅接受 `zh | en`。

### 4.3 后端不存语言

语言是纯展示参数，**不写入数据库、不写入 session、不写入 case 记录**。同一份数据在不同请求下可返回不同语言的投影。

## 5. 前端改动

### 5.1 引入 i18n

现状：无 i18n 依赖，`src` 下 670 行含中文，分布如下（Top 8）：

| 文件 | 含中文行数 |
|---|---|
| `views/CaseDetailView.vue` | 126 |
| `views/BimView.vue` | 81 |
| `views/AboutView.vue` | 72 |
| `utils.ts` | 47 |
| `views/AcceptanceView.vue` | 46 |
| `views/StartInspectionView.vue` | 27 |
| `views/KnowledgeView.vue` | 27 |
| `components/RectificationPanel.vue` | 24 |

方案：引入 `vue-i18n@11`，新建 `src/i18n/{index.ts, zh.ts, en.ts}`。

- `zh.ts` 为唯一事实源，`en.ts` 按同一 key 结构镜像；缺 key 时回退中文并在开发模式告警。
- 词条按页面分命名空间：`nav.*`、`common.*`、`case.*`、`bim.*`、`acceptance.*`、`about.*`、`status.*`、`error.*`。
- 预计 800–1000 条词条，其中约 150 条是 `status` / `result` / `risk_level` 枚举，优先处理（复用面最广）。

不选自建 `t()` 的原因：模板内插值、复数、命名空间回退需要手写，量大时容易漏 key 且无编译期检查。

### 5.2 语言切换控件

组件 `src/components/LanguageMenu.vue`：

- 触发按钮文案固定为 **`Language`**（不随语言变化），带 `Languages` 图标。
- 点击展开下拉，两项：**`简体中文`**、**`English`**，当前项打勾。
- 点击后立即切换，无二次确认，不弹「查看原文」。

放置位置：

1. **登录页右上角**：`AccessGate.vue` 外层容器加绝对定位的右上角插槽。
2. **登录后左侧导航栏底部**：`AppShell.vue` 的 `.sidebar-foot` 内、`.connection` 之上。

### 5.3 导航与路由标题

`AppShell.vue` 的 `nav` 与 `secondaryNav` 数组当前硬编码 `label`，改为 `labelKey`，模板中 `$t(labelKey)`。

`router.ts` 的 `meta.title` 是 `document.title` 的来源，改为 `meta.titleKey`，在 `router.afterEach` 中用 `i18n.global.t()` 解析，并为两种语言分别设置 `document.title`。

### 5.4 不翻译的原文区域

以下内容在英文模式下**原样显示中文**，不做任何机器翻译，也不加「查看中文原文」之类的降级入口：

- 上传的施工方案正文与解析结果（`SiteNote.body`、`paragraphs[].text`）
- 规范条文原文（`Rule.text`）
- 方案原文附件预览

英文模式下这些区域的标题（如「方案原文」→「Source Document」）翻译，正文保持中文。

## 6. 后端改动

### 6.1 新增模块 `app/translation.py`

**这是一个功能函数，不是 Agent**：不做规划、不调用业务工具、不写 case、不进图编排。

```python
def translate_fields(payload, lang: str) -> Any:
    """按字段白名单翻译展示字段，返回同结构副本；lang=zh 时原样返回。"""

def translate_texts(texts: list[str], lang: str, domain: str = 'safety') -> list[str]:
    """批量翻译，带缓存与占位符保护。"""
```

要点：

| 项 | 设计 |
|---|---|
| 模型调用 | 复用 `model_client` 的 HTTP 通道，`purpose='translation'`；默认复用 `MODEL_BASE_URL/KEY/NAME`，允许 `TRANSLATE_MODEL` 覆盖 |
| 并发 | 一次请求内多字段合并为单次调用（数组输入），避免 N 次请求 |
| 缓存 | 新表 `translation_cache(input_hash, lang, domain, output_text, model, created_at)`，命中直接返回；建表用 `CREATE TABLE IF NOT EXISTS`，不动现有表 |
| 幂等 | 同一文本同一语言只译一次，切换语言来回不重复计费 |
| 失败降级 | 超时或模型报错时返回**中文原文**并记录日志，不抛 500、不阻断页面 |
| 长度控制 | 单次批量上限约 4000 字符，超限自动分片 |

### 6.2 占位符保护

翻译前把不可译片段替换为占位符，译后还原：

- GUID：`0FOHK4aT910wgskSbVHn0U`、`2riKNFXuDAvQJxT4q2Dk7a`
- 规范编号：`GB55034-2022`、`JGJ80-2016`、`GB 55034`
- 条款号：`4.2.1`、`第 5.1.3 条`
- 案例/任务/运行 ID：`CASE-20261019-1A75FF`、`TASK-*`、`RUN-*`
- 规则 ID：`RULE-*`
- 数值 + 单位：`1.2 m`、`2.5 m`、`17.3 m`、`50 mm`

配套一份**术语表**，固定译法，保证同一概念前后一致：

| 中文 | English |
|---|---|
| 安全案例 / Safety Case | Safety Case |
| 风险候选 | Risk Candidate |
| 检查项 | Check Item |
| 控制措施 | Control Measure |
| 整改 | Rectification |
| 复核 | Verification |
| 补证 | Additional Evidence |
| 时空冲突 | Spatiotemporal Conflict |
| 待审核 / 待整改 / 待复核 | Pending Review / Pending Rectification / Pending Verification |
| 板边 | Slab Edge |
| 临边 | Open Edge |

### 6.3 翻译字段白名单

只翻译下列字段，其余（结构键、枚举原值、ID、时间戳）一律不动。

| 数据对象 | 翻译字段 | 不翻译 |
|---|---|---|
| `CaseRecord` | `title`、`request_text`、`assumptions[]`、`findings[].hazard`、`findings[].uncertainties[]`、`findings[].narrative.summary`、`findings[].checks[].name/note`、`controls[].action`、`controls[].verification_requirements[]`、`review.comment`、`implementation.comment`、`verification.remaining_risk`、`task_spec.clarification` | `case_id`、`status`、`bim_guids`、`rule_ids`、`as_of`、`model_*`、`allowed_actions` |
| `Finding` | `hazard`、`uncertainties[]`、`narrative.summary`、`checks[].note` | `result`、`risk_level`（枚举，前端 i18n 映射） |
| `Control` | `action`、`verification_requirements[]` | `status`、`control_id`、`version` |
| `AgentEvent` | `rationale`、`input_summary` | `node`、`tool`、`status`、`seq` |
| `Run` | `execution_plan.strategy`、`subtasks[].title`、`replanning.reason`、`evidence_gaps[].message/action`、`assurance.issues[].message`、`evidence_trace.facts[].property`、`nodes[].label` | 所有 ID、`permission`、`depends_on` |
| `Rule` | 无（`text` 为原文，保留中文） | `standard`、`clause`、`rule_id` |
| `SiteNote` | 无（原文保留） | `body`、`paragraphs[].text` |
| `Evidence` | `label`（若为生成的中文描述） | `observation` 原始值、`provenance` |

### 6.4 流式分析的处理（关键取舍）

现状：分析过程通过 `run_stream` 逐字推送中文增量。

英文模式下的三种做法：

| 方案 | 体验 | 成本 | 结论 |
|---|---|---|---|
| A. 增量实时翻译 | 逐字出英文 | 每 200ms 一次调用，断句破碎，费用最高 | 不采用 |
| B. 中文增量 + 结束后整体替换 | 先闪中文再变英文 | 一次翻译 | 不采用（违反「完全展示」） |
| C. 英文模式不渲染增量，显示生成中骨架，结束后一次性渲染译文 | 干净，无中文闪现 | 一次翻译 | **采用** |

实现：`run_stream` 的 SSE 协议与后端逻辑**完全不动**；仅前端在 `locale === 'en'` 时忽略 `delta` 消息，只更新进度状态，收到完成事件后调用翻译接口拿整段译文再渲染。

代价：英文模式下看不到逐字输出。这是可控的展示层代价，不影响业务。

### 6.5 Word 导出英文版

现状：`word_report.py` 的标题、表头、`STATUS` 映射全部硬编码中文，路由为：

```
GET /api/cases/{case_id}/export?format=docx
```

改动：

1. 路由增加 `lang: str = Query('zh', pattern='^(zh|en)$')`，透传 `export_case(case_id, format, lang)`。
2. `word_report.py` 抽出 `WORD_TEXT = {'zh': {...}, 'en': {...}}`，包含文档标题、章节标题、表头、状态标签、固定句式。
3. `report(bundle, lang='zh')`：固定文案取词条表，动态字段经 `translate_fields` 处理。
4. 英文排版适配：英文平均比中文长 30–50%，需调整表格列宽、标题字号，并允许长文本换行分页。
5. **规范条文原文与方案原文段落保持中文**，与网页端一致；仅章节标题与分析性文字译为英文。

前端 `CaseDetailView.vue` 的导出调用改为携带 `&lang=${store.locale}`，导出文件名后缀区分 `_EN.docx`。

## 8. 分阶段实施

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| S1 | `store.locale` + `LanguageMenu` 组件 + 两个挂载点 + 请求头 | 切换后刷新页面语言保持；两种入口位置正确；移动端不遮挡 |
| S2 | 静态文案 i18n：导航、路由标题、登录页、按钮、表单、状态枚举 | 全站无残留中文（原文区域除外）；`document.title` 随语言变化 |
| S3 | `translation.py` + 缓存表 + 占位符 + 术语表；接入智能助手回答 | 英文模式下回答为英文；GUID/规范编号/数值原样保留；重复文本命中缓存 |
| S4 | 接入案例工作台的动态字段（findings / controls / review / verification） | 案例详情页全英文；切换回来中文完整无损 |
| S5 | 接入 Agent 运行记录、计划与依据、补证清单 | 运行轨迹可读；无中文残句 |
| S6 | Word 英文导出 + 排版适配 | 英文模式下下载英文报告；表格不溢出；原文段落保持中文 |
| S7 | 全量回归与边界检查 | 见第 9 节 |

## 9. 验证方案

### 9.1 功能验证

1. 登录页右上角切换 → 页面文案整体切换，无残留中文（原文区除外）。
2. 侧栏底部切换 → 导航、面包屑、`document.title`、状态标签同步变化。
3. 刷新、关闭浏览器重开 → 语言选择保持。
4. 英文模式下发起一次检查 → 分析结果为英文，结束后一次性呈现，无中文闪现。
5. 英文模式下导出 Word → 文档为英文版，规范原文段落仍为中文。

### 9.2 不产生副作用（重点）

切换语言前后对比以下计数，必须完全一致：

```sql
SELECT COUNT(*) FROM cases;
SELECT COUNT(*) FROM case_events;
SELECT COUNT(*) FROM runs;
SELECT COUNT(*) FROM acceptance_results;
```

- 切换本身不发起任何业务 POST。
- 翻译调用只写 `translation_cache`，若复用 `model_calls` 记日志则以 `purpose='translation'` 区分，**不得计入业务 Agent 调用统计**。
- 同一案例在中英文下 `status`、`risk_level`、`allowed_actions`、`bim_guids`、`rule_ids` 必须逐字段相等。

英文长度膨胀需要专项检查：侧栏导航项、顶部面包屑、按钮组、表格表头、案例状态徽标、Word 表格列宽。检查宽度断点 1280 / 1100 / 850。

抽取 10 条案例文本人工核对：术语一致性、数字与单位、规范编号、GUID、是否出现漏译或过度意译。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 翻译模型不可用 | 英文页面出现中文 | 降级返回原文并提示；不阻断业务 |
| 术语不一致 | 同一概念多种译法 | 固定术语表 + 缓存，禁止逐次自由发挥 |
| 英文过长撑破布局 | 按钮/表格溢出 | 允许换行、调整列宽、必要时缩字号 |
| 翻译成本 | 重复调用计费 | 哈希缓存命中率通常较高；批量合并请求 |
| 漏译字段 | 页面中英混杂 | 字段白名单 + 前端扫描残留中文的检查脚本 |
| 误改业务 | 破坏现有闭环 | 严格禁止改动第 7 节清单；回归必须全绿 |

## 11. 第一版边界

- 不翻译用户上传的施工方案、项目资料原文、规范条文原文。
- 不提供「查看中文原文」切换。
- 不改变英文提问的业务处理能力：用英文提问仍按中文语义链路处理，回答再译为英文展示。
- 不引入自主决策的翻译 Agent，翻译是纯函数式服务。
- 英文模式不展示逐字流式输出。
